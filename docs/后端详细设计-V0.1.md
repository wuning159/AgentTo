# 文件智能协同平台

## 后端详细设计 V0.1

---

> 归档说明：本文形成于后端技术基线最终确认之前，不再作为当前执行依据。后端开发顺序以《AgentTo 后端开发路线 V0.1》和 `docs/superpowers/plans/2026-07-16-agentto-backend-phase-0-foundation.md` 为准。本文保留用于回看早期设计，后续会在对应业务阶段重新整理详设。

> 本文用于指导后端第一阶段搭建。内容以当前已经确认的技术边界为准，工作流的实际产品和流转规则尚未确定，因此通过适配接口隔离，不在第一阶段绑定具体工作流引擎。

> 依赖版本核对时间：2026 年 7 月 15 日。后续升级版本时需要重新执行构建、数据库迁移和回归测试。

## 1. 这一阶段要完成什么

第一阶段不是直接把整套业务做完，而是先建立一个可以持续开发的后端基础工程，目标包括：

- Spring Boot 项目能够在本机启动；
- 数据库表结构由 Flyway 统一管理；
- 建立任务、轮次、文件版本、C 咨询、Agent 运行和审计等核心模型；
- 工作流通过 `WorkflowGateway` 接入，先使用本地模拟实现；
- Spring AI 完成依赖和配置边界，正常启动时通过环境变量读取模型密钥；
- 提供统一异常处理、参数校验、健康检查和基础测试；
- MySQL、MinIO、Redis、Elasticsearch 和模型服务均按真实服务接入；公司工作流和企业微信待现状确认后适配。

这一阶段暂不实现：

- 完整的文件审批页面接口；
- 公司现有工作流的真实适配器；
- 企业微信通知和单点登录；
- 文件解析、预览转换和版本差异；
- 完整的 RAG、Embedding 和 Rerank 链路；
- 自审 Agent 和秘书组 Agent 的正式 Prompt；
- 可视化流程配置。

这些内容不是被放弃，而是在基础工程稳定后按业务确认结果逐步接入。

## 2. 技术基线

| 项目 | 当前选择 | 说明 |
| --- | --- | --- |
| Java | 21 | 使用 LTS 版本 |
| 构建工具 | Maven | 使用本机 `D:\DevTools\Maven` |
| Spring Boot | 4.0.x | 与 Spring AI 2.0.0、Spring Cloud Alibaba 2025.1.0.0 统一验证 |
| Spring AI | 2.0.0 | 通过 `spring-ai-bom` 管理依赖版本 |
| Web | Spring MVC | 当前业务以后台管理和文件处理接口为主，不采用响应式栈 |
| 数据访问 | Spring Data JPA | 先满足核心业务表和事务处理 |
| 数据库 | MySQL 8.x | 正式业务数据库 |
| 本地和测试数据库 | 阿里云 MySQL | 测试使用独立 `agentto_test` 库，不使用内存数据库替代 MySQL |
| 数据库迁移 | Flyway | 正式表结构只能通过迁移脚本修改 |
| 接口校验 | Jakarta Validation | 请求参数和业务命令分层校验 |
| 健康检查 | Spring Boot Actuator | 为本机、Docker 和服务器部署提供探针 |
| 测试 | JUnit 5、Spring Boot Test | 单元测试和少量集成测试 |

Spring AI 2.0.0 支持 Spring Boot 4.0.x 和 4.1.x。对话模型先按 OpenAI 兼容协议预留，后续可以配置 DeepSeek、智谱或通义千问的地址、模型名和密钥。Embedding 和 Rerank 仍通过独立 TEI HTTP 服务接入，不和对话模型绑在一起。

## 3. 工程组织

后端使用单个 Maven 项目，目录为：

```text
backend/
├─ pom.xml
├─ mvnw
├─ mvnw.cmd
├─ .mvn/wrapper/
├─ src/main/java/com/agentto/platform/
│  ├─ AgentToApplication.java
│  ├─ common/
│  ├─ task/
│  ├─ document/
│  ├─ consultation/
│  ├─ workflow/
│  ├─ agent/
│  └─ audit/
├─ src/main/resources/
│  ├─ application.yml
│  ├─ application-local.yml
│  ├─ application-dev.yml
│  ├─ application-prod.yml
│  └─ db/migration/
└─ src/test/java/com/agentto/platform/
```

项目按业务模块分包，每个模块内部再区分接口、应用服务、领域对象和基础设施。第一阶段不拆 Maven 多模块，也不拆微服务。

### 3.1 common

保存跨模块通用能力：

- 统一 API 错误结构；
- 全局异常处理；
- 分页参数和分页结果；
- 时间、ID 和审计字段；
- 当前用户接口；
- 基础配置和通用校验。

`common` 不能反向依赖任何具体业务模块。

### 3.2 task

负责文件任务和处理轮次：

- 创建任务；
- 保存任务名称、类型、主导人和当前状态；
- 创建和切换 `review_round_id`；
- 记录当前轮次的节点和版本；
- 查询任务概要和时间线。

### 3.3 document

负责逻辑文件和文件版本：

- `document_id` 表示同一份逻辑文件；
- `document_version_id` 表示某次实际上传版本；
- 记录对象存储 Key、原始文件名、大小、类型和哈希；
- 文件内容由 MinIO 保存，MySQL 只保存元数据；
- 正式版本不覆盖，只能追加新版本。

第一阶段只建立模型和存储接口，不实现真实 MinIO 上传。

### 3.4 consultation

负责 C 咨询和主导人的处理说明：

- 一轮咨询对应一个咨询批次；
- 每位 C 对指定材料包提交“有意见”或“无意见”；
- 正式意见和主导人的处理说明分别保存；
- 已提交意见不能直接覆盖，修改需要保留历史记录；
- C 是否必须全部提交等规则由工作流和业务配置共同决定。

### 3.5 workflow

负责隔离 AgentTo 和具体工作流底座。核心接口暂定为：

```java
public interface WorkflowGateway {
    WorkflowInstanceRef start(StartWorkflowCommand command);

    WorkflowTaskRef findCurrentTask(String workflowInstanceId, String userId);

    void complete(CompleteWorkflowTaskCommand command);

    void returnTask(ReturnWorkflowTaskCommand command);

    void withdraw(WithdrawWorkflowCommand command);

    WorkflowHistorySnapshot history(String workflowInstanceId);
}
```

第一阶段提供 `InMemoryWorkflowGateway`，用于本机启动和接口测试。真实工作流确认后新增适配器，不修改任务、文件和 Agent 模块。

工作流回调必须携带外部事件 ID。系统先检查该事件是否已经处理，再更新内部状态，避免重复回调导致流程被推进两次。

### 3.6 agent

负责自审 Agent 和秘书组 Agent 的统一运行框架：

- Agent 定义；
- Prompt 版本；
- 任务上下文快照；
- 模型和工具网关；
- 运行状态、耗时、Token、错误和结果；
- 当前责任人的采用、修改或放弃记录。

第一阶段只建立下面两个边界：

```java
public interface AgentExecutionGateway {
    AgentRunResult execute(AgentRunRequest request);
}

public interface TaskContextAssembler {
    TaskContextSnapshot assemble(TaskContextRequest request);
}
```

真实实现使用 Spring AI `ChatClient`，工具调用通过 `ToolCallback` 或 `@Tool` 注册。模型地址、模型名和密钥从环境变量读取；缺少配置时直接报告，不生成伪造分析结果。

### 3.7 audit

审计分成两类：

- 业务表自身的创建人、创建时间、更新人和更新时间；
- 独立审计事件，记录任务、轮次、文件版本、操作人、操作类型、结果、时间、IP、文件哈希和关联 ID。

审计事件只追加，不通过普通业务接口修改或删除。

## 4. 总体关系

![基于 Spring AI 的总体架构](assets/technical-architecture-spring-ai.png)

关键边界如下：

1. 前端只调用 AgentTo 的业务接口，不直接调用工作流系统；
2. 业务记录先在 AgentTo 中保存成功，再通过 `WorkflowGateway` 推进流程；
3. 工作流只保存流转所需标识，不保存文件正文和完整 Agent 上下文；
4. Agent 只在自审和秘书组终审运行，不能主动完成工作流任务；
5. MySQL 和 MinIO 是正式数据来源，Elasticsearch 索引允许重建；
6. Redis 只能保存缓存、锁和短期状态，不能成为正式业务记录的唯一存储。

## 5. 第一批数据表

下面是后端陆续需要建立的核心表。字段命名使用小写下划线，业务主键统一使用 UUID 字符串。

| 表 | 用途 | 关键关联 |
| --- | --- | --- |
| `at_task` | 文件任务 | `task_id` |
| `at_task_participant` | 主导人、C、秘书组、老板和 I | `task_id`、用户 ID、角色 |
| `at_review_round` | 每次完整处理轮次 | `task_id`、`review_round_id` |
| `at_document` | 逻辑文件 | `task_id`、`document_id` |
| `at_document_version` | 文件版本元数据 | `document_id`、`review_round_id` |
| `at_consultation_batch` | 某轮 C 咨询批次 | `review_round_id`、材料包版本 |
| `at_consultation_opinion` | C 的正式咨询意见 | 咨询批次、C 用户、意见状态 |
| `at_opinion_resolution` | 主导人的逐条处理说明 | 咨询意见、处理结果、修改版本 |
| `at_workflow_mapping` | 内外部流程和待办映射 | `task_id`、外部流程 ID |
| `at_workflow_event` | 工作流回调幂等记录 | 外部事件 ID |
| `at_agent_definition` | Agent 节点、角色和版本 | Agent 编码、启用版本 |
| `at_agent_run` | 一次 Agent 运行 | 任务、轮次、文件版本、状态 |
| `at_context_snapshot` | 运行时正式上下文快照 | Agent 运行、快照哈希 |
| `at_audit_event` | 独立审计事件 | 业务对象、操作人和时间 |

基础工程的 `V1` 迁移只建立当前最小任务链需要的五张表：`at_task`、`at_review_round`、`at_task_participant`、`at_workflow_mapping` 和 `at_audit_event`。文件版本、C 意见和 Agent 运行等表跟随对应功能在后续迁移中增加，不在业务尚未确认时一次设计死。

## 6. 第一批接口

为了验证工程结构，第一阶段只实现一条最小业务链：

### 6.1 健康检查

```http
GET /actuator/health
```

用于本机、Docker 和服务器探活。

### 6.2 创建任务

```http
POST /api/v1/tasks
Content-Type: application/json

{
  "title": "年度经营计划",
  "documentType": "PLANNING",
  "leaderUserId": "user-001"
}
```

处理顺序：

1. 校验标题、文件类型和主导人；
2. 创建 `at_task`；
3. 创建第一条 `at_review_round`；
4. 写入主导人参与关系；
5. 调用本地 `WorkflowGateway` 创建模拟流程实例；
6. 保存工作流映射；
7. 写入审计事件；
8. 返回任务和当前轮次信息。

### 6.3 查询任务

```http
GET /api/v1/tasks/{taskId}
```

返回任务基本信息、当前轮次、主导人和工作流状态。暂不返回完整文件、意见和 Agent 结果。

## 7. 事务和一致性

### 7.1 数据库事务

同一次业务操作中的任务、轮次、参与人、映射和审计记录在一个 MySQL 事务中保存。

外部工作流调用不能真正加入 MySQL 本地事务。真实适配时采用下面的方式：

1. 业务数据先保存为待同步状态；
2. 通过 Outbox 记录待执行的工作流命令；
3. 异步调用公司工作流；
4. 成功后更新映射和状态；
5. 失败后按规则重试并保留错误信息。

第一阶段的本地工作流实现不引入消息中间件，但接口和状态字段按这一方向设计。

### 7.2 幂等

- 创建任务支持调用方请求 ID；
- 工作流回调按外部事件 ID 去重；
- 文件版本按文件哈希和业务请求 ID 防止重复上传；
- Agent 运行按任务、轮次、文件版本、Agent 定义版本和触发请求 ID 去重。

### 7.3 并发

任务和轮次表保留乐观锁版本号。用户提交意见、处理说明或审批决定时，必须同时校验当前轮次、当前节点和记录版本，防止在旧页面上提交过期操作。

## 8. 配置和运行环境

### 8.1 test

只用于自动化测试：

- 纯业务规则使用不依赖外部服务的单元测试；
- 数据库、Redis、MinIO 等集成测试连接阿里云隔离测试资源；
- 本地模拟工作流；
- 关闭非测试目标的模型自动调用，避免无关测试产生真实费用。

### 8.2 local 和 dev

用于开发机和后续阿里云开发环境：

- MySQL、MinIO、Redis 和 Elasticsearch 地址通过环境变量提供；
- 工作流适配器按实际系统配置；
- 外部模型密钥只通过环境变量或密钥文件提供；
- 不把密码、Token 和密钥提交到项目。

### 8.3 prod

用于正式环境：

- 禁止自动创建表，只执行审核后的 Flyway 迁移；
- Actuator 只开放必要探针；
- 日志不输出正文、密钥和敏感上下文；
- 所有外部调用设置连接超时、读取超时和有限重试；
- 删除、导出和管理接口需要单独权限和审计。

## 9. 异常返回

统一错误结构：

```json
{
  "code": "TASK_NOT_FOUND",
  "message": "任务不存在",
  "traceId": "01J...",
  "details": []
}
```

业务异常使用稳定错误码，不把 Java 类名、SQL、远程响应正文或堆栈直接返回前端。日志中通过 `trace_id` 关联一次请求。

## 10. 测试范围

第一阶段至少包含：

- 应用上下文启动测试；
- 创建任务应用服务测试；
- 创建任务接口测试；
- 查询不存在任务的异常返回测试；
- 工作流本地实现测试；
- Flyway 迁移执行测试；
- 模型未配置时应用仍能启动的测试；
- 重复请求 ID 不会重复创建任务的测试。

后续接入真实 MySQL 和工作流时，再增加 Testcontainers 和适配器契约测试。

## 11. 第一阶段验收标准

满足下面条件才算基础工程搭建完成：

1. `./mvnw test` 全部通过；
2. `test` 配置不调用真实外部服务，正常运行配置能够连接真实中间件；
3. 健康检查返回可用状态；
4. 可以创建任务并查询；
5. 数据库迁移能够从空库完整执行；
6. 模型地址、模型名和密钥通过环境变量提供，项目中不存在明文密钥；
7. 业务模块不直接依赖 Flowable 或公司工作流 SDK；
8. 项目中不存在明文密码和密钥；
9. README 写清启动、测试和配置方法。

## 12. 后续服务器检查

收到阿里云服务器地址和访问方式后，先只做检查，不直接删除或覆盖现有服务：

- 操作系统、CPU、内存、磁盘和剩余空间；
- Docker 和 Docker Compose 版本；
- 当前运行的容器、镜像、网络和数据卷；
- 已占用端口；
- MySQL、Redis、Elasticsearch、MinIO 等服务是否已经存在；
- 现有服务版本、账号获取方式、数据目录和备份情况；
- 防火墙、安全组和内网访问范围；
- 是否已有反向代理、域名和证书；
- 当前工作流服务和企业微信回调地址；
- 哪些容器属于其他项目，不能修改。

检查结果确认后，再决定复用、升级或新增容器。任何涉及停止、替换、删除容器和数据卷的操作，都需要单独确认。

## 13. 后续开发顺序

1. 搭建基础工程和本地启动环境；
2. 建立核心迁移脚本和任务最小业务链；
3. 增加文件元数据和 MinIO 适配；
4. 确认并接入公司现有工作流；
5. 完成 C 咨询、主导人处理和多轮循环；
6. 建立 Spring AI 运行框架和自审 Agent；
7. 接入 Elasticsearch、TEI 和 RAG；
8. 完成版本差异和秘书组 Agent；
9. 联调企业微信通知、待办和跳转；
10. 补充部署、监控、备份和恢复。
