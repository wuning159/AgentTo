# AgentTo 独立 RAG 服务设计 V0.1

## 1. 这次要做什么

在 AgentTo 之外建立一套独立的 RAG 服务。它负责知识文件的保存、解析、分块、向量化、索引、召回、精排和过程记录，并提供一个只面向技术管理员的管理后台。

AgentTo 仍然负责正式文件业务、人员权限、工作流、Agent 上下文和最终结果。RAG 服务不推进审批，也不保存审批结论，只向 AgentTo 返回带来源的检索依据。

第一版需要跑通下面这条完整链路：

1. 技术管理员登录；
2. 上传 Word、PDF 或 Excel 文件；
3. 查看文件解析、清洗、分块、向量化和写入索引的进度；
4. 查看实际切片内容和定位信息；
5. 输入问题，分别观察关键词召回、向量召回、RRF 融合和 Rerank 结果；
6. 查看每个候选切片在各阶段的分数、名次、耗时和降级情况。

## 2. 与 AgentTo 的边界

| 内容 | AgentTo | 独立 RAG 服务 |
| --- | --- | --- |
| 正式文件任务和版本 | 负责 | 只接收需要建立索引的文件版本标识 |
| 工作流和企微通知 | 负责 | 不参与 |
| 用户、部门和业务权限 | 负责 | 接收已经计算好的检索范围 |
| 文件解析、分块和索引 | 调用 | 负责 |
| 关键词、向量、混合召回和精排 | 调用 | 负责 |
| Agent Prompt 和上下文组装 | 负责 | 不负责 |
| 自审、秘书组 Agent | 负责 | 只返回证据片段 |
| RAG 调试与运行观察 | 查看必要摘要 | 技术管理后台完整展示 |

正式接入时，AgentTo 通过服务接口提交文件版本和检索范围。管理后台的手工上传入口主要用于知识资料维护、问题排查和参数验证，不替代 AgentTo 的正式文件入口。

## 3. 工程结构

新系统放在 `E:\AgentTo\rag-service`：

```text
rag-service/
  backend/    Spring Boot 4.1、Spring AI 2.0
  frontend/   Vue 3、TypeScript、Vite、Element Plus
```

后端先做成一个模块化单体，解析、索引、检索和管理接口放在同一个应用里，避免一个人开发时维护过多服务。TEI Embedding、TEI Rerank、Elasticsearch、MinIO 和 MySQL 仍是独立中间件，通过 HTTP 或标准客户端调用。

## 4. 复用原则

`E:\RagAiDemo` 已经跑通过一套较完整的 RAG 链路，本次优先复用它已经验证的实现和交互，不重新发明一套相同逻辑。

| 能力 | 处理方式 |
| --- | --- |
| Word、PDF、Excel 解析 | 迁移解析器，调整包名、异常结构和元数据格式 |
| 文本清洗和结构化分块 | 迁移主体逻辑，补充分节、Sheet、页码等来源定位 |
| TEI Embedding 和 Rerank | 迁移 HTTP 客户端和失败回退逻辑 |
| MinIO 对象存储 | 迁移存储抽象和 MinIO 实现 |
| Elasticsearch 索引和 KNN | 复用查询思路，适配当前 ES 版本和新索引结构 |
| 关键词 + 向量 + RRF + Rerank | 迁移现有算法、分数和名次记录方式 |
| 入库阶段记录和查询 Trace | 迁移模型和展示思路，改为独立 RAG 领域字段 |
| 知识工作台和文档详情交互 | 复用页面布局、时间线、切片表格、候选池和分数列 |
| FAQ 表格模板和 FAQ 行切片 | 不迁移 |
| 问答、AI 助手、群组和普通用户功能 | 不迁移 |

原项目只作为来源，不在原目录上修改。迁移到新工程后再做版本升级和领域收敛。

## 5. 后端模块

后端按职责分为下面几个模块：

- `auth`：技术管理员登录、会话、退出和当前用户；
- `document`：知识文件、版本、对象存储地址、哈希和状态；
- `ingestion`：异步入库任务、阶段记录、解析、清洗、分块和索引；
- `embedding`：统一封装 TEI Embedding；
- `retrieval`：关键词召回、向量召回、RRF、Rerank 和降级；
- `trace`：查询过程、候选切片、各阶段分数、耗时和错误；
- `admin`：工作台、文档详情、切片查看、健康状态和调试接口；
- `integration`：后续给 AgentTo 调用的稳定服务接口。

Spring AI 2.0 用在统一的文档模型和后续与 AgentTo 的 Agent 能力对接上。TEI 和 Elasticsearch 仍通过独立适配器封装，业务层不直接依赖具体模型地址或索引名称。

## 6. 文件入库链路

一次入库使用同一个 `ingestion_job_id` 串起全部阶段：

1. 校验扩展名、文件大小和内容类型；
2. 计算 SHA-256，保存原文件到 MinIO；
3. 在 MySQL 创建文件、版本和入库任务；
4. 根据文件类型调用 Word、PDF 或 Excel 解析器；
5. 清洗文本并保留页码、章节、Sheet、行号等定位信息；
6. 按结构和长度分块；
7. 调用 TEI 生成向量；
8. 把切片正文、元数据和向量写入 Elasticsearch；
9. 保存切片摘要、阶段耗时和最终状态；
10. 页面轮询任务状态并展示完整时间线。

第一版不处理扫描 PDF 的 OCR，不解析 Office 原生批注、修订记录、宏和复杂图表语义。解析失败时保留原文件、失败阶段和错误摘要，可以重新执行入库。

## 7. 检索链路

默认参数先采用：关键词召回 20 条、向量召回 20 条、RRF 合并 20 条、Rerank 取前 10 条、最终返回 5 条。

检索过程如下：

1. 校验请求中的知识范围；
2. 对问题生成查询向量；
3. Elasticsearch 分别执行关键词和向量检索；
4. 在 Java 内按 RRF 合并候选；
5. 调用 TEI Rerank 对合并后的候选重新打分；
6. 返回切片正文、文件、版本、定位信息和各阶段分数；
7. 把这次查询和候选池保存为 Trace。

TEI Rerank 不可用时回退到 RRF 排序；TEI Embedding 不可用时可以只执行关键词检索；Elasticsearch 不可用时明确返回检索服务不可用，不伪造结果。

## 8. 数据保存

MySQL 保存管理员、会话、文件和版本元数据、入库任务、阶段事件、切片摘要、查询 Trace 和候选分数。MinIO 保存原文件。Elasticsearch 保存可重建的切片索引和向量。

索引中的每条切片至少包括：

- `chunk_id`、`document_id`、`version_id`；
- 正文和标题；
- 页码、章节、Sheet、行号等定位信息；
- 文件类型和业务分类；
- 可见范围；
- Embedding 模型、向量维度和索引版本；
- 当前有效状态。

原文件和 MySQL 元数据是正式来源，Elasticsearch 索引可以重建。

## 9. 技术管理后台

第一版页面包括：

- 登录页；
- 总览：文件、切片、成功率、最近任务和服务状态；
- 文件管理：上传、筛选、状态和失败重试；
- 文件详情：版本、入库时间线、参数、切片样例和完整切片列表；
- 检索实验室：输入问题、调整召回数量，查看四个阶段的结果；
- Trace：查看问题、耗时、降级、候选池、分数和名次变化；
- 服务状态：MySQL、MinIO、Elasticsearch、Embedding 和 Rerank。

页面只面向技术管理员，不建设普通员工入口，也不在这里做最终问答和 Agent 对话。

## 10. 第一版验收标准

- 能用技术管理员账号登录和退出；
- 能上传 `.docx`、`.pdf`、`.xlsx` 文件；
- 页面能看到文件从上传到索引完成的阶段和状态；
- 页面能查看真实切片正文及来源定位；
- 输入问题后能得到真实的关键词、向量、RRF 和 Rerank 结果；
- 每次检索能保存 Trace，并展示候选切片各阶段分数和名次；
- Rerank 不可用时页面能看到降级信息，检索仍能返回 RRF 结果；
- 前端和后端可以在本地启动，中间件连接现有服务器；
- `E:\RagAiDemo` 保持不变。
