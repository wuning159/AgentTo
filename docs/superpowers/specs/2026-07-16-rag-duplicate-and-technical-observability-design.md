# RAG 重复治理与技术执行可视化设计

## 1. 这次要解决什么

当前系统已经能够完成文件入库、混合检索、精排和 Trace 保存，但还有两个问题需要补上：

1. 相同文件重复上传后，会生成两套文档、版本、分块和索引数据；检索时，相同内容可能占据多个最终名次。
2. 页面能看到任务状态和各阶段耗时，但还不能回答“这一阶段具体怎么处理、用了什么参数、输入输出是什么、分数怎么算出来的”。

这次把两件事一起设计，是因为去重本身也是检索执行过程的一部分，技术管理员需要同时看到去重前后的数据变化。

## 2. 已确认的处理原则

### 2.1 上传和检索采用双层去重

- 上传时按文件 SHA-256 判断是否为完全相同的文件。
- 检索时按规范化后的分块内容计算内容哈希，避免相同内容重复占据最终结果。
- 上传去重减少无意义的数据和模型计算；检索去重负责兜底，处理历史重复数据以及不同文件中的相同内容。
- 检索去重不能删除 Trace 中的原始候选。被合并的候选仍然保留，并标明被哪个候选代表。

### 2.2 技术执行页面采用融合结构

- 以“流水线 + 技术检查器”为页面主体。
- 顶部保留完整时间线，用于查看阶段顺序、执行状态、耗时、数量和降级情况。
- 底部保留完整执行报告，用于复盘和审计，默认折叠。
- 自然语言负责解释“做了什么”，技术参数、公式、输入输出样本和原始数据负责解释“具体怎么做的”。

## 3. 上传去重

### 3.1 判断范围

当前系统还没有知识空间或租户隔离，因此第一版在整个 RAG 服务范围内按 SHA-256 判断完全重复。

上传流程调整为：

1. 校验文件名和文件类型。
2. 读取文件并计算 SHA-256。
3. 查询是否已有相同 SHA-256 的文档版本。
4. 如果已经存在，直接返回已有文档和版本，不再写入 MinIO，不创建新文档、版本和入库任务。
5. 如果不存在，继续执行对象存储、文档建档和入库任务创建。

第一版不提供“仍然重复上传”入口。用户如果上传了相同文件，页面明确提示“该文件已经入库”，并提供已有文档的查看入口。

接口仍然返回成功响应，但上传结果增加：

- `duplicate`：是否命中完全重复文件；
- `documentId`、`versionId`：新建或已有的数据编号；
- `jobId`：重复文件为 `null`，新文件为实际入库任务编号；
- `message`：供页面展示的说明。

这种返回方式可以让页面正常引导用户，不把重复上传当成系统故障。

### 3.2 当前历史重复数据

上传拦截只阻止后续新增重复数据，不主动删除当前数据库、MinIO 和 Elasticsearch 中的历史数据。

历史重复数据先由检索去重兜底。后续如果需要治理历史数据，再单独提供扫描报告和人工确认后的清理入口，不能在本次改动中自动删除。

## 4. 检索结果去重

### 4.1 内容规范化

分块内容在计算检索去重哈希前执行确定性的规范化：

1. 使用 Unicode NFKC 规范化；
2. 连续空白合并为一个空格；
3. 去掉首尾空白；
4. 保留标点、数字和正文内容，不做同义词或语义判断；
5. 对规范化结果计算 SHA-256。

第一版只处理内容相同或仅空白表现不同的情况，不做语义近似去重。

### 4.2 去重位置

去重放在 RRF 计算之后、Rerank 之前：

```text
关键词召回 + 向量召回
        ↓
RRF 计算全部候选分数
        ↓
按规范化内容哈希合并
        ↓
截取 fusionLimit
        ↓
截取 rerankLimit 进入精排
        ↓
截取 finalLimit 形成最终结果
```

这样做有两个原因：

- 可以先利用两路召回的完整排名计算 RRF，不改变融合逻辑。
- 重复内容不会占用有限的 Rerank 名额，也不会挤掉本应进入最终结果的不同内容。

### 4.3 代表候选选择

同一内容哈希下存在多个候选时，按以下顺序选择代表候选：

1. RRF 分数更高；
2. RRF 排名更靠前；
3. `chunkUid` 字典序更靠前，作为稳定兜底规则。

其余候选标记为 `DUPLICATE`，记录代表候选的 `chunkUid`。代表候选标记为 `KEPT`。

最终结果只包含 `KEPT` 候选；完整 Trace 同时包含 `KEPT` 和 `DUPLICATE` 候选。

## 5. 技术执行详情页

文档入库和检索 Trace 使用同一套页面骨架，不各做一套交互。

### 5.1 页面顶部：任务摘要

展示：

- 文件名或检索问题；
- 任务编号或 Trace ID；
- 开始和结束时间；
- 总耗时；
- 输入数量和最终输出数量；
- 是否发生降级；
- 性能或数据质量提示。

性能提示只依据真实数据产生，例如 Rerank 耗时占总耗时过高；不能使用固定的模拟告警。

### 5.2 第一层：完整时间线

文档入库时间线：

```text
保存 → 解析 → 清洗 → 分块 → 向量化 → 建立索引 → 完成
```

检索时间线：

```text
查询预处理 → 关键词召回 → 查询向量生成 → 向量召回
→ RRF 融合 → 内容去重 → 精排 → 最终结果
```

每个节点显示：

- 等待、执行中、完成、降级、跳过或失败；
- 阶段耗时；
- 输入和输出数量；
- 一句结果摘要。

点击节点后，下面的技术检查器切换到该阶段。

### 5.3 第二层：技术检查器

技术检查器是默认工作区，包含四个页签。

#### 处理说明

使用自然语言说明该阶段做了什么，以及为什么需要这一步。例如：

> RRF 不直接比较 BM25 分数和向量相似度，而是分别使用两路排名计算贡献，再把贡献相加。

#### 参数与公式

展示本次执行时的真实参数快照，而不是读取当前配置后冒充历史配置。

RRF 阶段至少展示：

```text
RRF(d) = Σ 1 / (k + rankᵢ(d))
```

当前实现 `k = 60`。选中某个候选后，需要拆开显示关键词排名贡献、向量排名贡献和相加结果。

分块阶段至少展示：

- 分块器：结构化段落分块；
- 目标长度：500 字符；
- 最大长度：800 字符；
- 重叠长度：80 字符；
- 大段落拆分顺序：句子、次级标点、字符硬切。

向量化和索引阶段至少展示模型标识、向量维度、批量大小、索引名称和实际写入数量。页面不能展示密码、令牌或带凭据的完整服务地址。

#### 输入输出样本

根据阶段展示少量有代表性的真实样本：

- 解析：原始段落、标题、表格与解析块；
- 清洗：清洗前后对比及规则命中数量；
- 分块：来源段落、生成分块、标题路径和重叠内容；
- 向量化：文本、维度和向量前若干维，不能把完整向量全部渲染到表格；
- RRF：两路排名、各自贡献和融合排名；
- 内容去重：代表候选、被合并候选和内容哈希；
- 精排：精排前后排名变化。

#### 原始响应

展示经过脱敏和截断的 JSON，用于技术排查。以下内容不能返回页面：

- 密码、Token 和 API Key；
- HTTP Authorization 请求头；
- 数据库和中间件连接密码；
- 完整向量数组；
- 超过页面限制的大段二进制或原始文件内容。

### 5.4 第三层：完整执行报告

完整执行报告默认折叠。展开后按时间顺序展示：

- 事件时间；
- 阶段和状态；
- 自然语言执行记录；
- 输入输出数量；
- 参数快照；
- 降级、跳过和失败原因；
- 阶段耗时。

完整报告用于还原一次任务发生了什么，不能只根据当前数据库状态临时拼接。历史任务必须使用任务执行当时保存的参数和结果。

## 6. 后端数据设计

### 6.1 入库阶段

保留现有 `rag_ingestion_stage`，增加 `technical_detail_json` 字段。每个阶段在执行完成或失败时保存结构化详情。

建议的公共结构：

```json
{
  "summary": "按标题和段落组合生成分块",
  "inputCount": 32,
  "outputCount": 37,
  "parameters": {
    "targetChars": 500,
    "maxChars": 800,
    "overlapChars": 80
  },
  "metrics": {
    "oversizedParagraphs": 2,
    "tableChunks": 3
  },
  "samples": [],
  "raw": {}
}
```

样本只保存少量、截断后的内容，避免阶段表无限增长。

### 6.2 检索 Trace

`rag_query_trace` 增加：

- `rank_constant`：本次 RRF 使用的常量；
- `deduplicated_count`：本次合并的重复候选数量；
- `execution_report_json`：完整阶段报告和参数快照。

`rag_query_candidate` 增加：

- `content_hash`：规范化内容哈希；
- `dedupe_status`：`KEPT` 或 `DUPLICATE`；
- `duplicate_of_chunk_uid`：被合并到哪个代表候选。

现有候选分数和排名字段继续保留，RRF 单路贡献可以通过 `rank_constant` 和两路排名准确计算，不重复存储派生分数。

## 7. 接口调整

### 7.1 上传接口

```http
POST /api/admin/documents
```

返回结果增加 `duplicate` 和 `message`。重复文件的 `jobId` 为 `null`，前端不启动入库任务轮询。

### 7.2 入库任务详情

```http
GET /api/admin/ingestion/jobs/{jobId}
```

每个阶段增加 `technicalDetail`。页面根据阶段类型解释字段，不在后端返回 HTML。

### 7.3 检索 Trace 详情

```http
GET /api/admin/retrieval/traces/{traceUid}
```

增加：

- 本次检索限制参数；
- `rankConstant`；
- `deduplicatedCount`；
- 完整执行报告；
- 候选的内容哈希和去重关系。

现有字段保留，避免召回实验室和已有 Trace 页面同时失效。

## 8. 页面落点

- 文档上传抽屉继续展示实时入库时间线，任务完成后可以进入文档处理详情页。
- 文档详情页增加“处理过程”入口，展示完整技术执行详情。
- 检索 Trace 抽屉升级为融合后的执行详情页结构。
- 召回实验室完成检索后保留结果展示和 Trace 入口，不在当前页面重复渲染完整报告。

## 9. 第一版不做的内容

- 不做语义近似去重；
- 不自动删除历史重复文档、MinIO 文件和 Elasticsearch 数据；
- 不调整 PDF 分块策略；
- 不保存完整 Embedding 向量到执行报告；
- 不把日志文件原文直接返回给浏览器；
- 不在这次改动中增加模型效果评测和多模型对比。

## 10. 验收标准

- 同一个文件连续上传两次，只产生一份文档、版本、对象存储文件和索引数据；第二次上传能够进入已有文档。
- 历史重复分块不再重复占据最终结果，最终结果中的规范化内容哈希唯一。
- 完整 Trace 仍能看到被合并的候选及其代表候选。
- 文档入库每个阶段都能看到真实耗时、输入输出数量、参数和样本。
- 检索 Trace 可以看到完整时间线，点击阶段后能查看技术说明、参数、公式和样本。
- RRF 页面使用实际 `k` 和实际排名计算，页面展示值与后端保存值一致。
- Embedding 或 Rerank 降级时，时间线、检查器和完整报告三处显示一致。
- 页面和接口不暴露密码、Token、API Key、Authorization 头和完整向量。
- 后端单元测试、前端单元测试和前端构建全部通过。
