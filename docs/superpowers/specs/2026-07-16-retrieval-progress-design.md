# 召回实验室检索进度设计

## 1. 要解决的问题

召回实验室目前通过一个同步接口执行混合检索。用户点击“运行混合检索”以后，只能看到按钮处于加载状态，直到关键词召回、向量召回、融合和精排全部完成后才能得到结果。

这次调整的目标是让用户在等待期间看到检索实际执行到了哪一步，同时了解每个阶段的耗时和产出数量。页面展示的必须是真实状态，不使用按时间模拟的百分比进度。

## 2. 页面交互

用户提交检索后，查询区域下方显示一条线性进度：

1. 关键词召回
2. 查询向量生成
3. 向量召回
4. 结果融合
5. 精排
6. 完成

每个节点有“等待、执行中、完成、降级、跳过、失败”六种状态。

- 执行中的节点高亮并显示动态效果。
- 完成后显示本阶段耗时和产出数量。
- 查询向量生成只显示耗时，不显示数量。
- Embedding 或 Rerank 不可用时，节点显示黄色“已降级”和原因，检索继续执行。
- 无法继续完成检索时，当前节点显示红色失败信息，已经完成的节点保留。
- 完成后沿用现有结果表格和 Trace 入口，不另做一套结果页面。

示例：

```text
关键词召回       查询向量生成       向量召回       结果融合       精排          完成
20 条 / 86 ms    315 ms             20 条 / 68 ms  30 条 / 3 ms  15 条 / 2.8 s  8 条
```

## 3. 后端处理方式

管理后台改用“异步检索任务 + 短轮询”。原有同步检索接口继续保留，避免影响后续 AgentTo 或其他服务调用 RAG。

### 3.1 接口

创建任务：

```http
POST /api/admin/retrieval/jobs
```

请求参数沿用现有检索参数。接口立即返回任务编号，不等待检索结束。

查询进度：

```http
GET /api/admin/retrieval/jobs/{jobUid}
```

返回内容包括：

- 任务总体状态；
- 当前阶段；
- 六个阶段各自的状态、耗时、数量和说明；
- 检索完成后的 `RetrievalResponse`；
- 任务失败时的错误信息。

现有接口继续保留：

```http
POST /api/admin/retrieval/search
```

### 3.2 任务执行

检索任务由独立线程执行。`HybridRetrievalService` 在每个实际步骤开始和结束时上报阶段事件，进度管理器只负责保存最新快照，不参与检索逻辑。

第一版的任务快照保存在应用内存中，完成或失败后保留 30 分钟，最多保留最近 500 条。它只服务于管理后台的短期观察，不承担正式业务存档。服务重启后未完成的临时任务不恢复，最终结果和完整 Trace 仍按现有机制保存。以后如果 RAG 服务需要多实例部署，可以把任务快照实现替换为 Redis，前端接口不需要改变。

## 4. 前端处理方式

点击检索后的处理顺序：

1. 调用创建任务接口，取得 `jobUid`。
2. 每 500 毫秒查询一次任务进度。
3. 根据后端返回的阶段快照更新进度条。
4. 任务完成后停止轮询并展示结果。
5. 页面离开、重新检索或组件销毁时停止旧轮询，避免重复请求。

按钮在任务执行期间保持禁用。用户修改输入内容不会影响已经提交的任务。

## 5. 降级和失败规则

- Embedding 失败：查询向量生成节点显示“已降级”，向量召回标记为跳过；继续使用关键词结果进行融合和精排。
- Rerank 失败：精排节点显示“已降级”，使用融合排序生成最终结果。
- 关键词召回、融合、Trace 保存或其他不可恢复异常：任务标记失败，前端展示具体阶段和错误原因。
- 轮询偶发失败：前端继续重试；连续失败 3 次后停止轮询并提示用户重新执行检索。
- 新检索开始时清除上一次页面进度，但已经生成的 Trace 不受影响。

## 6. 测试范围

后端测试：

- 创建任务后能够立即获得任务编号；
- 各检索阶段按真实执行顺序更新；
- 阶段耗时和数量正确写入快照；
- Embedding、Rerank 降级时任务仍能完成；
- 不可恢复异常能够保留失败阶段和错误信息；
- 原同步检索接口行为保持不变。

前端测试：

- 后端阶段状态能够正确映射为页面节点；
- 数量、毫秒和秒级耗时格式正确；
- 降级、失败、完成状态显示正确；
- 任务完成、失败和组件销毁后停止轮询。

最后使用真实检索请求验证进度不是一次性跳到完成，并检查最终结果及 Trace 与原有功能一致。
