```
1c2d896 fix(asset): 过期 PENDING 缺元数据时流式重算 SHA
```

**行为（必须保持）：**

- 规范对象键：`content-assets/sha256/{前2位}/{64位小写hex}`。**忽略调用方传入的 objectKey。**
- `rag_content_asset` 状态：`PENDING | READY | DELETE_PENDING | DELETE_FAILED`。
- 上传：先插 PENDING 租约，再流式 put。同一 SHA 复用。未过期租约等待；过期可接管。迟到的 owner **不能** `markReady`。
- **共享规范键在迟到所有者失败时不得删除**（竞态输家不得 `delete` 别人的对象）。
- 生产上传路径禁止 `readAllBytes` / `getBytes()`；两遍流式（摘要 + put），字节数必须等于 `UploadedDocument.contentLength`。
- 引用扫描必须覆盖 **全部历史** `rag_document_version`：`content_asset_id` **或** `sha256`。本仓库没有 `rag_parsed_asset` / `rag_media_catalog`。
- 未引用 READY 先写 `unreferenced_since`；**满 168h**（`!unreferencedSince.isAfter(now-168h)`）才进删除，再删对象 + 行。
- 过期 PENDING：对象有 sha256 元数据则比对；**元数据缺失必须流式重算**（8KB 缓冲）。匹配 → READY + 即时补偿；不匹配或读失败 → 保持 PENDING、释放租约，**不删共享键**。禁止把「无元数据」当成匹配。
- `rag.scheduling.enabled`：测试 profile 为 false；`@Scheduled` 仅在 true 时启用。
- `DocumentService` 走 `ContentAssetService.storeOrReuse(UploadedDocument.from(file))` + `requireReadyForReference`；落库用 `TransactionTemplate`，不要把对象存储 I/O 包在超长 `@Transactional` 里。

## 4. 已知坑（做过才知道）

- `UploadClaim` 的 boolean 字段必须叫 `waiting`（不要用工厂方法名 `waiting()`）。
- `PollingContentAssetPendingWaiter` 不要加额外 `Duration` 构造器（会坏 Spring）。测试用 `@Primary` `ControllablePendingWaiter`。
- `InMemoryObjectStorage.blockNextPut()` 不是按 key，是全局 one-shot；`blockNextPut` / `clear` 里要重建 latch。
- `requireReadyForReference` 的等待在锁外；锁 + touch 用 `TransactionTemplate` REQUIRED。
- `ContentAsset.markDeletePending` **不要**设租约，这样同一次 `runOnce` 还能认领删除。
- SHA 唯一：不要插第二行；唯一约束冲突 → READY 复用或 busy。
- 前端 `uploadResult.test.ts` 仍用假的 `manual/*.docx` key，那是 DTO 单测，可以保持。
- 本地 `npm` 默认 registry 可能是 npmjs，lockfile 是 npmmirror。动 lockfile 时继续用 npmmirror。
- 需要时 `chmod +x mvnw`，**不要提交** 这个 mode 变化。
- 本仓库没有 ArchUnit `document.asset` 业务包规则。
- 本仓库 **没有** `.github` workflow（直到 PR #3）。合 #3 前 GitHub 上没有检查。
