# HopFresh 工作流智能体开发交接说明

> 文档状态：开发切换说明  
> 更新时间：2026-07-17  
> 使用方式：切换到 `E:\hopfresh` 开发后，先完整阅读本文，再结合 HopFresh 源码、已有调研资料和 GitNexus 索引制定实施计划。  
> 当前原则：本文只整理已经确认的方向、第一阶段准备做的内容和需要继续确认的问题，不把尚未确认的业务流转写死。

## 1. 这次方向为什么调整

项目不再建设独立的 AgentTo 系统。

现在的目标是直接依托 HopFresh，在现有 BPM 工作流基础上增加智能审查能力。账号、组织、权限、文件服务、工作流、企业微信、AI 模型管理、知识库和前端框架都使用 HopFresh 已有能力。

原来规划的以下内容停止继续建设：

- 独立的 `AgentTo backend`；
- 独立账号、部门、角色和登录会话；
- 独立工作流服务；
- Spring Boot 4 和 Spring AI 2.0 升级；
- 独立 AgentTo 前端；
- 第一阶段接入 `E:\AgentTo\rag-service`；
- 从 HopFresh 拆出 BPM 或 AI 模块。

`E:\AgentTo\rag-service` 继续保留，后续如果 HopFresh 自带 RAG 无法满足要求，再作为扩展方案评估。第一阶段直接使用 HopFresh 自带知识库和 RAG。

## 2. 现在要做成什么

在 HopFresh 的 BPM 待办详情中增加“智能审查”能力。

用户进入允许使用 Agent 的任务节点后，可以手动发起智能审查。系统读取当前文件、附件、流程信息、历史人工意见和知识库内容，动态生成 Prompt，调用 HopFresh 已配置的模型，保存完整执行过程，并把审查结果展示在当前任务页面。

Agent 只提供辅助分析，不能：

- 修改文件；
- 上传新版本；
- 提交正式审批意见；
- 通过、驳回或退回任务；
- 自动推进工作流；
- 代替任何人作出正式决定。

即使 Agent 被关闭、没有运行、运行失败或者模型不可用，原有 BPM 流程仍然必须正常办理。

## 3. 第一阶段的 Agent 范围

第一阶段只考虑两种业务 Agent：

1. 文件主导人自审 Agent；
2. 秘书组终审 Agent。

C 审查阶段暂时不接入 Agent。

两种 Agent 共用一套运行框架，通过配置区分：

- Agent 类型；
- 适用流程；
- 适用任务节点；
- 可使用的模型；
- Prompt 模板；
- 知识库；
- 执行策略；
- 结果可见范围；
- 是否启用。

第一阶段由用户手动触发，不在进入节点时自动运行。

## 4. HopFresh 已有能力怎么使用

### 4.1 System

直接使用 HopFresh 的：

- 登录和当前用户；
- 用户、部门、角色和岗位；
- 菜单、按钮和接口权限；
- 数据权限；
- 操作日志。

不再建立第二套用户体系。

### 4.2 Infra

直接使用 HopFresh 的：

- 文件上传、下载和临时访问地址；
- 配置、字典和公共组件；
- Redis；
- 定时任务和异步执行基础；
- 监控和日志。

当前文件和附件通过 Infra 文件能力读取。Agent 不直接访问底层对象存储。

### 4.3 BPM

直接使用 HopFresh 的：

- 流程模型和部署；
- 流程实例；
- 用户任务；
- 待办、已办和历史；
- 审批、驳回、退回、转办、委派、加签、减签和撤回；
- Flowable 评论和流程变量；
- 任务监听器、执行监听器和状态事件；
- 企业微信通知。

Agent 集成不能把模型调用直接写进 `BpmTaskServiceImpl`，也不能直接查询 Flowable 数据库表。

BPM 需要向 AI 模块提供一份受控的“智能审查上下文”，内容至少包括：

- 流程定义 Key；
- 流程实例 ID；
- 当前任务 ID；
- 当前任务节点 Key 和名称；
- 业务 Key；
- 发起人；
- 当前处理人；
- 流程变量；
- 当前文件和附件引用；
- 已完成任务；
- 历史审批意见；
- 驳回和退回记录；
- 当前用户是否有权发起本次 Agent。

建议在 `yudao-module-bpm-api` 中增加专门接口，例如：

```java
public interface BpmAgentContextApi {

    BpmAgentContextRespDTO getContext(
            Long userId,
            String processInstanceId,
            String taskId);
}
```

具体接口名和字段需要和 BPM 开发确认，不能仅凭本文直接定死。

### 4.4 AI

直接使用 HopFresh `yudao-module-ai` 中的：

- API Key 管理；
- 模型管理；
- 模型工厂；
- DeepSeek 等模型调用；
- Spring AI 1.1.0；
- 流式输出；
- Prompt 和角色相关实现；
- Tool/MCP 基础能力；
- 知识库和 RAG。

第一阶段不升级 Spring AI，也不重写模型工厂。

建议在 `yudao-module-ai-server` 中新增 `workflowagent` 业务域，避免把文件审查逻辑塞进通用聊天 Service：

```text
yudao-module-ai-server
└─ workflowagent
   ├─ controller
   ├─ service
   ├─ context
   ├─ prompt
   ├─ rag
   ├─ runtime
   ├─ dal
   └─ convert
```

最终目录和包名需要结合 AI 开发的意见确定。

### 4.5 企业微信

沿用 BPM 当前的企业微信通知链路，不为 Agent 单独建设消息系统。

第一阶段 Agent 只在 HopFresh 页面中运行和查看结果，不主动发送正式业务通知。以后如果要增加“Agent 已完成”提醒，再复用现有企微消息接口。

## 5. Agent 和 BPM 的关系

建议采用“页面手动触发 + AI 模块主动读取 BPM 上下文”的方式。

```text
BPM 任务详情页
    ↓ 手动点击智能审查
AI WorkflowAgentController
    ↓ 校验当前用户和节点
BpmAgentContextApi
    ↓ 返回流程、文件和历史意见
Infra FileApi
    ↓ 读取文件内容
HopFresh RAG
    ↓ 返回知识依据
动态 Prompt 组装
    ↓
HopFresh 模型工厂 / Spring AI
    ↓
保存 Agent 运行、阶段、Prompt 和结果
    ↓ SSE 或轮询
BPM 任务详情页展示结果
```

不建议第一阶段使用 Flowable ServiceTask 自动调用模型，原因是：

- 当前明确要求用户手动触发；
- Agent 不应该成为工作流继续流转的前置条件；
- 模型调用时间长、可能失败；
- 用户需要在当前页面观察执行过程；
- 以后是否自动运行可以通过配置增加，不需要第一阶段写进 BPMN。

## 6. 节点绑定

Agent 是否可用不能只写死在前端。

建议用以下信息进行配置：

```text
流程定义 Key
+ 任务节点 Key
+ Agent 类型
+ 允许的系统角色
+ Prompt 版本
+ 模型 ID
+ 知识库 ID
+ 执行策略
+ 启用状态
```

页面根据后端返回的权限和节点配置决定是否显示“智能审查”按钮；后端在真正执行前再次校验。

总经办确认流程后，主要调整 BPMN 和节点绑定，不应重写 Agent Runtime。

## 7. 文件和历史意见怎么进入上下文

第一阶段优先复用 HopFresh 流程表单、流程变量和文件服务。

Agent 每次运行需要锁定本次实际使用的数据：

- 当前文件地址、文件名和文件标识；
- 附件列表；
- 文件提取后的正文；
- 当前流程实例和任务；
- 历史任务；
- 所有已经提交的人工意见；
- 驳回、退回和老板意见；
- 本次使用的 Prompt 版本；
- 本次使用的知识库和召回结果；
- 模型和调用参数。

即使流程变量或文件以后发生变化，也必须能够还原某次 Agent 当时使用的内容。

文件版本到底由 BPM 表单、现有业务表还是新增文件协同表负责，需要和 BPM 开发确认。Agent 运行表至少要保存本次文件标识、内容哈希和上下文快照，不能只保存最终结论。

## 8. 动态 Prompt

Prompt 模板和实际上下文分开管理。

模板负责相对稳定的内容：

- Agent 角色；
- 审查目标；
- 审查规则；
- 输出格式；
- 禁止操作；
- Planning、Review、Reflection、Finalize 阶段要求。

运行时上下文负责本次实际数据：

- 当前用户和部门；
- 当前流程和任务节点；
- 当前文件正文；
- 附件；
- 历史文件和意见；
- 知识库召回内容；
- 当前处理人提出的额外要求。

最终 Prompt 是模板和上下文组合后的完整结果，每次运行都需要保存。

第一阶段继续使用完整上下文策略：

- 不主动压缩；
- 不静默截断；
- 不把三轮作为硬限制；
- 预计超过模型窗口时展示警告，但仍按实际请求执行；
- 模型拒绝后保存真实错误，不伪造成功结果。

## 9. HopFresh 自带 RAG 怎么接

第一阶段直接使用 HopFresh 的知识库能力：

- `ai_knowledge`：知识库；
- `ai_knowledge_document`：知识文档；
- `ai_knowledge_segment`：知识分段；
- 文档解析和切片；
- Embedding；
- 向量召回；
- 可选 Rerank。

Agent 定义或节点绑定需要配置知识库 ID。

一次审查的建议过程：

1. 根据当前文件、节点和审查目标形成检索问题；
2. 调用 HopFresh 知识库召回；
3. 保存召回的 segment、文档、分数和参数；
4. 将召回内容连同来源一起放入 Prompt；
5. 最终结果中的证据能够回到对应知识文档。

需要向 Spring AI 开发确认：

- 当前知识库实际使用哪个 VectorStore；
- 当前环境的向量索引是否持久化；
- Embedding 模型是否已经配置可用；
- Rerank 是否已经启用；
- 检索入口应该调用哪个 Service；
- 多实例部署时知识索引如何共享；
- 当前切片策略和文件解析是否满足 Word、PDF、Excel；
- 是否已有知识库权限过滤。

第一阶段不接 `E:\AgentTo\rag-service`，但数据模型不要把 HopFresh RAG 的内部实现写死到 Agent 业务逻辑中。

## 10. Agent 运行阶段

一套 Agent Runtime 支持四个阶段：

1. **Planning**：确认审查目标、范围和优先级；
2. **Review**：结合文件、流程意见和知识依据形成问题与建议；
3. **Reflection**：检查遗漏、矛盾、证据不足和偏离目标；
4. **Finalize**：形成结构化报告和可阅读结论。

四个阶段属于同一个逻辑 Agent，不是四个独立系统。

执行策略可以配置：

- `SIMPLE`：单次模型调用；
- `PLAN_REVIEW`：Planning + Review；
- `FULL`：四阶段完整执行。

第一阶段演示使用哪一种，需要结合交付时间和 Spring AI 开发的现有能力确认。页面和数据模型应允许以后切换。

## 11. 建议新增的数据

可以复用 HopFresh 已有的 `ai_api_key`、`ai_model` 和知识库相关表。

工作流智能体建议新增以下数据。表名只是讨论稿，需要按 HopFresh 命名和现有 AI 模块习惯调整：

| 数据 | 用途 |
|---|---|
| Agent 定义 | 自审、秘书组终审等逻辑 Agent |
| Prompt 模板和版本 | 草稿、发布版本和回滚 |
| 流程节点绑定 | 流程、节点、角色、Agent、模型和知识库 |
| Agent 运行 | 一次正式或调试运行的主记录 |
| Agent 阶段记录 | Planning、Review、Reflection、Finalize 的状态和耗时 |
| 上下文快照 | 文件、流程、意见、RAG 和变量来源 |
| 最终 Prompt | 本次真正发送给模型的完整内容 |
| 模型调用记录 | 模型、参数、Token、耗时、重试和错误 |
| 结构化报告 | 问题、风险、证据和建议 |
| 人工反馈 | 采纳、忽略、修正和备注 |

大文本是否直接放 MySQL `longtext`，还是经 Infra 文件服务保存并在表中记录引用，需要和 AI 开发确认。

正式记录不能被新的运行覆盖。重新运行必须产生新的 `runId`。

## 12. 前端需要做什么

项目有现成 HopFresh 前端，不再建设新前端工程。

### 12.1 BPM 任务详情页

在现有任务详情中增加“智能审查”区域：

- 是否允许智能审查；
- 手动运行按钮；
- 当前运行状态；
- 阶段时间线；
- 当前执行到哪一步；
- 是否发生重试或降级；
- 审查问题、风险、证据和建议；
- 知识库引用；
- 采纳、忽略和备注；
- 历史运行记录。

Agent 区域是 BPM 任务详情的一部分，不改变原有审批操作区。

### 12.2 AI 技术管理页

在现有 AI 管理菜单下补充：

- Agent 定义；
- Prompt 模板和版本；
- 流程节点绑定；
- Agent 运行记录；
- 上下文查看；
- 最终 Prompt；
- 模型调用和 Token；
- RAG 召回内容；
- 错误、重试和耗时；
- 功能开关。

第一阶段不要求一次做完所有管理页面，但运行过程必须有地方查看，不能只留下服务日志。

## 13. 权限和结果可见范围

沿用 HopFresh 权限体系，并增加业务数据校验。

当前确定的结果范围：

| 内容 | 文件主导人 | C | 秘书组 | 老板 | 技术管理员 |
|---|---|---|---|---|---|
| 自审 Agent 结果 | 可见 | 不可见 | 不可见 | 不可见 | 可见并记录审计 |
| 秘书组 Agent 结果 | 不可见 | 不可见 | 可见 | 默认不可见 | 可见并记录审计 |
| 完整 Prompt | 不可见 | 不可见 | 不可见 | 不可见 | 可见并记录审计 |
| 模型原始输出 | 不可见 | 不可见 | 不可见 | 不可见 | 可见并记录审计 |
| Token 和模型参数 | 不可见 | 不可见 | 不可见 | 不可见 | 可见 |

秘书组 Agent 结果以后是否给老板看，仍待确认。

技术管理员查看完整文件、Prompt 和原始输出时，需要记录查看审计。

## 14. 失败、重试和降级

- Agent 未运行不影响 BPM；
- Agent 运行失败不影响 BPM；
- 页面关闭不应取消后台任务；
- 相同流程实例、任务和 Agent 类型同时只允许一个正式运行；
- 用户可以取消运行，但已完成阶段仍保留；
- 网络超时和限流可以有限重试；
- 自动切换备用模型默认关闭；
- RAG 失败时是否允许不带知识继续运行，需要做成配置，页面明确显示；
- 重新运行创建新记录，不覆盖旧结果；
- 原始异常只在技术管理页和日志中按权限展示。

第一阶段可以先用现有异步执行能力，不急于增加消息队列，但运行调度接口需要保留以后替换的空间。

## 15. Tool / MCP

HopFresh 已有 Tool/MCP 基础，但不是第一阶段交付前置条件。

如果第一阶段需要使用，只允许只读能力：

- 读取流程上下文；
- 读取当前文件和附件；
- 查询历史意见；
- 查询知识库；
- 查询用户和部门。

禁止修改文件、上传版本、提交意见、办理流程和发送正式通知。

建议默认关闭，等基础 Agent 链路稳定后再打开。

## 16. 第一阶段建议实施顺序

### 第一步：确认 HopFresh 运行环境

- 后端、前端、System、Infra、BPM、AI 和企业微信模块如何启动；
- 使用单体 `yudao-server` 还是独立服务；
- 当前 Nacos、MySQL、Redis、文件服务和模型配置；
- 当前 AI 模型是否能真实调用；
- 当前知识库是否能上传、切片和召回；
- 当前 BPM 是否能建立流程、发起任务和完成审批。

### 第二步：建立一条可测试的 BPM 流程

下午由用户在 HopFresh 中建立流程。

至少需要记录：

- 流程定义 Key；
- 自审节点 Key；
- C 审查节点 Key；
- 秘书组节点 Key；
- 老板节点 Key；
- 文件字段名称；
- 附件字段名称；
- 参与人变量；
- 意见保存方式；
- 退回后的节点行为。

流程细节后续可以调整，但节点标识和 Agent 上下文读取方式要先确定。

### 第三步：打通最小智能审查

先完成一条最小链路：

```text
BPM 任务详情
→ 手动运行
→ 取得当前文件和流程上下文
→ 调用一个已配置模型
→ 保存运行记录
→ 页面展示结果
```

该链路先不要求四阶段、RAG、Tool/MCP 和完整管理后台。

### 第四步：接动态 Prompt 和 HopFresh RAG

- Prompt 模板；
- 节点和角色变量；
- 文件正文；
- 历史意见；
- 知识库检索；
- 引用保存；
- 最终 Prompt 保存。

### 第五步：补运行阶段和可视化

- Planning、Review、Reflection、Finalize；
- SSE 或轮询进度；
- 时间线；
- Token、耗时和错误；
- 上下文、Prompt 和 RAG 查看器；
- 人工反馈。

### 第六步：绑定实际业务流程

总经办确认业务后，再调整 BPMN、节点映射、参与人和退回规则。

## 17. 需要和 BPM 开发确认的问题

1. 当前准备使用单体 `yudao-server`，还是 BPM 独立服务；
2. 业务模块读取流程实例、当前任务、历史任务和评论的推荐接口；
3. 是否应该新增 `BpmAgentContextApi`，还是已有合适接口；
4. 当前文件字段和附件字段在流程表单、变量中怎么保存；
5. 文件上传新版本后，旧文件引用如何保留；
6. 审批意见、退回意见和评论分别存在哪里；
7. 如何判断当前用户确实有权办理当前任务；
8. 自审和秘书组节点的 `taskDefinitionKey` 如何固定；
9. 多人会签和 C 全部完成的状态如何读取；
10. 退回后流程实例是否继续使用，还是重新发起；
11. BPM 任务详情页最合适的扩展位置；
12. 企微通知与任务链接当前怎么生成；
13. Agent 运行状态是否需要作为流程变量；

## 20. 第一阶段验收标准

满足以下条件才算完成第一阶段集成：

1. 原有 BPM 在关闭 Agent 时可以完整运行；
2. 自审或秘书组节点可以手动运行 Agent；
3. 非允许节点和无权限用户不能运行；
4. Agent 可以读取当前文件和 BPM 历史意见；
5. Agent 可以调用 HopFresh 自带知识库进行召回；
6. Agent 可以调用一个真实模型；
7. 页面能看到运行状态，不会一直无反馈等待；
8. 页面能展示最终问题、证据、风险和建议；
9. 技术人员能查看上下文、RAG、最终 Prompt 和模型调用；
10. 每次重新运行都保留历史；
11. Agent 失败不会影响任务审批；
12. 后端接口、前端页面和关键异常场景没有 500；
13. 新增能力有单元测试和必要的真实集成测试。
